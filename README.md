# Позиции товаров в поиске Wildberries

Сервис каждый час собирает поисковую выдачу Wildberries по 70 запросам (топ-200, город — Москва),
хранит историю позиций в SQLite и показывает её в веб-интерфейсе на Streamlit.

- **Веб-интерфейс:** https://wb-serp-tracker.streamlit.app
- **Код:** https://github.com/neldnermaksim/wb-serp-tracker
- **Данные:** ветка [`data`](https://github.com/neldnermaksim/wb-serp-tracker/tree/data) — SQLite-база со всей историей, обновляется после каждого сбора
- **Журнал сборов:** [GitHub Actions](https://github.com/neldnermaksim/wb-serp-tracker/actions/workflows/collect.yml)

## Что умеет интерфейс

- выбор запроса из 70 (формулировки как в исходной таблице, с поиском по вводу);
- выбор одного или нескольких товаров (ID), когда-либо найденных по запросу, — списком или
  кнопками «Топ-3/5/8», а также отметкой строк в полной выдаче;
- интерактивный график позиций: **1 — вверху**, при наведении — дата/время, ID и позиция;
  если товара не было в топе при очередном сборе, **линия прерывается** (позиция не выдумывается);
- таблица характеристик выбранных товаров: позиция и её изменение, цена, рейтинг, отзывы,
  срок доставки, продавец, фото и ссылка на карточку; выгрузка в CSV;
- вкладка «Выдача целиком» — топ-200 любого сбора с изменением позиций к предыдущему;
- сводка последнего сбора: сколько товаров пришло в топ и выбыло, кто сильнее всех вырос и упал;
- «Журнал сборов» — лента запусков и подробности каждого;
- светлая и тёмная темы (по настройке системы), адаптация под телефон.

## Как устроено

```
GitHub Actions (каждый час, цепочка запусков)
  └─ python -m wb_serp.publish pull      скачать базу из ветки data
  └─ python -m wb_serp.collect           70 запросов × 2 страницы через headless Chromium
  └─ python -m wb_serp.publish push      проверить базу и выложить в ветку data
  └─ next: таймер окружения 50 мин → HH:04 → запуск следующего сбора
                                    │
                                    ▼
Streamlit Community Cloud: app.py ── скачивает базу из ветки data (проверка обновлений раз в 5 минут)
```

| Модуль | Что делает |
|---|---|
| `wb_serp/wb_client.py` | запросы к поиску WB изнутри браузера, прохождение антибот-проверки, повторы |
| `wb_serp/parsing.py` | разбор ответа API в наблюдения, расчёт срока доставки |
| `wb_serp/storage.py` | схема SQLite, запись сбора (только добавление) |
| `wb_serp/collect.py` | один полный сбор, CLI |
| `wb_serp/scheduler.py` | ежечасный запуск без GitHub Actions (сервер, Docker, локально) |
| `wb_serp/publish.py` | синхронизация базы с веткой `data` с защитой от потери истории |
| `wb_serp/analytics.py`, `charts.py`, `ui.py`, `app.py` | выборки, графики, оформление и веб-интерфейс |
| `scripts/verify_against_site.py` | сверка данных парсера с карточками на сайте |

### Сбор данных

- **Источник** — тот же поисковый API, которым пользуется сайт
  (`www.wildberries.ru/__internal/u-search/exactmatch/ru/common/v18/search`, сортировка «по популярности»,
  100 товаров на страницу). Для топ-200 берутся страницы 1 и 2; глубина настраивается: `--top-n` или `WB_TOP_N`.
- **Позиция** — порядковый номер товара в выдаче, как на сайте (порядок API совпадает с порядком карточек).
- **Город** — фиксированный `dest=1259570991`: именно его гео-сервис WB возвращает для адреса «Москва»
  с координатами центра (Красная площадь). Код зависит от района, поэтому зафиксирована одна точка.
- **Запросы** — `queries.txt`, копия Google-таблицы из ТЗ (проверено: совпадает с PDF). Обновить:
  `python -m wb_serp.queries --sync`.

| Поле | Откуда | Комментарий |
|---|---|---|
| позиция, nm_id | порядок и `id` товара в ответе | |
| цена | `sizes[].price.product` | цена со всеми скидками; сайт крупно показывает цену «с WB Кошельком», она на ~2% ниже и в API не приходит |
| рейтинг | `reviewRating` | «4,8» на карточке; у товара без оценок — `null` |
| количество отзывов | `feedbacks` | «15 575 оценок» |
| срок доставки, дни | `time1 + time2` (часы) | дата = момент сбора по МСК + часы + 1 ч; дней = дата − сегодня (сегодня 0, завтра 1) |
| продавец | `supplier` | название продавца, не бренд |

Недоступное поле сохраняется как `NULL`, ничего не подставляется.

**Сверка с сайтом** (`python scripts/verify_against_site.py`): на 510 карточках трёх запросов
совпали срок доставки (500/500), рейтинг (379/379), число оценок (457/457) и цена (501/501).

**Сверка позиций.** Сайт, открытый в чистом браузере с адресом «Москва, центр», и парсер в ту же минуту
дали одинаковый порядок: 40 из 40 позиций для «постельное белье евро» и «шелковое постельное белье»,
38 из 40 для «постельное белье 2 спальное» (два одинаковых комплекта одного продавца поменялись местами 1↔2).
Парсер каждый раз начинает с чистого профиля, поэтому видит выдачу нового покупателя — WB персонализирует
выдачу по истории просмотров, и в браузере с историей порядок может отличаться.

### База данных (SQLite)

| Таблица | Содержимое |
|---|---|
| `queries` | запросы в исходных формулировках и их порядок |
| `runs` | запуски: время, статус, глубина, город, сколько собрано |
| `query_runs` | результат по каждому запросу в запуске: время сбора, статус, сколько товаров у WB |
| `observations` | позиция, цена, рейтинг, отзывы, срок доставки — товар × запрос × запуск |
| `products` | справочник товаров: название, бренд, продавец |
| `v_observations` | представление «одна строка = товар в выдаче» со всеми полями из ТЗ |

История только дописывается: ни один код не удаляет и не изменяет прошлые наблюдения.
Объём: один сбор — около 14 тыс. строк, ~80 КБ в сжатой публикуемой базе (≈2 МБ в сутки).
`query_runs` позволяет отличить «товара нет в топе» (разрыв на графике) от «запрос не собрался»
(этот сбор не учитывается). Перед публикацией база проверяется (`PRAGMA integrity_check`
и «ни в одной таблице не стало меньше строк»), иначе публикация отменяется. Ветка перезаписывается
только если на GitHub её никто не изменил с момента скачивания (`--force-with-lease`), поэтому два
сборщика (облачный и локальный) не затрут данные друг друга.

## Запуск локально

Нужен Python 3.11+.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
python -m playwright install chromium
```

```bash
python -m wb_serp.collect              # один сбор: 70 запросов, ~3 минуты, база в data/serp.db
python -m wb_serp.collect --limit 3    # быстрый проверочный сбор
python -m wb_serp.scheduler --now      # сбор сейчас и далее каждый час (HH:05 МСК)
python -m wb_serp.scheduler --sync --minute 20   # страховка облака: собрать и опубликовать,
                                                 # только если GitHub Actions в этот час не собрал
streamlit run app.py                   # интерфейс на http://localhost:8501
pytest                                 # тесты
```

Чтобы посмотреть в интерфейсе облачные данные: `python -m wb_serp.publish pull` (скачает базу из ветки `data`).

## Развёртывание

1. **Сбор:** workflow `.github/workflows/collect.yml` (вручную — *Actions → Сбор выдачи WB → Run workflow*).
   Ежечасность обеспечивает цепочка: после сбора задание `next` ждёт на таймере окружения
   `hourly-timer` (50 минут, сервер при этом не занят), выравнивается на HH:04 и запускает следующий сбор.
   Окружение создаётся один раз: *Settings → Environments → New environment* `hourly-timer`,
   *Wait timer* = 50. Cron в :17 и :47 лишь перезапускает цепочку, если она оборвалась; сбор пропускается,
   если предыдущий был меньше 45 минут назад. Сборы идут строго по одному. Секреты не нужны.
2. **Интерфейс:** [share.streamlit.io](https://share.streamlit.io) → *Create app* → репозиторий
   `neldnermaksim/wb-serp-tracker`, ветка `main`, файл `app.py`.
3. (Необязательно) в *Settings → Secrets and variables → Actions → Variables* задать `APP_URL` — адрес
   приложения: после каждого сбора workflow откроет его, и бесплатное приложение не уснёт.

## Комментарий

**Время работы:** около 6 часов, включая исследование антибот-защиты WB и проверку данных на сайте.

**Сложности и решения**

- *Антибот WB.* С 2025 года поиск WB закрыт: без cookie `x_wbaas_token` API отвечает 403/498,
  а токен выдаётся только браузеру, прошедшему JS-проверку. Обычный headless-браузер WB распознаёт
  (по `HeadlessChrome` в User-Agent) и держит на странице проверки. Решение: полноценный Chromium
  в «новом» headless-режиме с обычным User-Agent; запросы к API идут через `fetch` изнутри страницы —
  с теми же cookie, заголовками (`deviceid`, `x-spa-version`) и TLS-отпечатком, что у сайта.
- *Токен «выгорает».* Примерно через 20–25 запросов WB снова требует проверку. Клиент ловит 498/403,
  страница заново проходит проверку, запрос повторяется; плюс паузы ~1–1,5 с между запросами
  и повторный проход по запросам, не собранным с первого раза.
- *Город.* Без `dest` WB определяет город по IP. Код для Москвы взят из гео-сервиса WB; выяснилось,
  что он зависит от района, поэтому зафиксирован центр Москвы.
- *Срок доставки.* В API есть только часы (`time1 + time2`). Простое «сейчас + часы» расходилось с сайтом
  у товаров, приезжающих в 23:xx. Правило «+1 час» подобрано на 1378 карточках и перепроверено
  скриптом сверки в другое время суток — 100% совпадений.
- *Устойчивость.* Каждый запрос сохраняется отдельной транзакцией (сбой посреди сбора не теряет уже
  собранное), не собранные запросы повторяются вторым проходом, после 3 ошибок подряд браузер
  перезапускается, после 6 — сбор останавливается с понятной причиной в журнале. Оборванный запуск
  закрывается при следующем.
- *Где хостить.* Нужен ежечасный запуск без участия человека и публичный интерфейс. Сбор идёт
  в GitHub Actions (WB пускает облачные IP), база публикуется в отдельную ветку одним коммитом
  (сжатая xz), Streamlit Cloud скачивает её и проверяет обновления по ETag.
- *Ненадёжный cron GitHub.* В первые часы GitHub выполнил лишь 2 из ~13 плановых запусков. Решение —
  самоподдерживающаяся цепочка: каждый запуск после сбора ставит следующий через таймер окружения
  (ожидание бесплатно и не занимает сервер), а cron остаётся страховкой для перезапуска цепочки.
- *Честный график.* Отсутствие товара в выдаче — разрыв линии, а упавший сбор не считается
  «отсутствием»: для этого результат каждого запроса в каждом запуске хранится отдельно.

**AI-инструменты:** Claude Code (Claude Opus 5.5) — исследование API и антибота, код, тесты,
проверка интерфейса в браузере.
